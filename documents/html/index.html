How it works

From two spec files to sealed evidence

One command compares the versions, classifies every change, and writes reports you can hand to a reviewer. A second command re-checks the evidence independently.

Compare

Point it at the old and new spec.

contractsutra compare \
  --before v1.json --after v2.json \
  --out reports

Gate

Exit code 2 stops the pipeline when the gate is crossed.

--fail-on breaking
--fail-on risky   # default
--fail-on none

Audit

Replay 12 checks and verify the seal.

contractsutra audit --dir reports \
  --out reports/audit
contractsutra verify --report \
  reports/audit/audit-report.json

Understand a change

Request and response are judged differently

A provider must keep accepting old requests and keep delivering old responses. That one idea drives every rule.

Client → Provider

Request

The provider must keep accepting what old clients send.

  • BREAKINGNew required field or parameter
  • BREAKINGTighter limit (maxLength down)
  • BREAKINGEnum value removed
  • SAFENew optional field
  • SAFELooser limit
Provider → Client

Response

The provider must keep delivering what old clients rely on.

  • BREAKINGField removed
  • BREAKINGType changed, or null now possible
  • BREAKINGStatus code or media type removed
  • REVIEWEnum value added, guarantee relaxed
  • SAFENew optional field

What it does not do

  • It compares specifications, not running services. A green gate is not proof of runtime compatibility.
  • JSON OpenAPI only for now: no YAML, GraphQL, AsyncAPI or protobuf.
  • Consumers are self-declared. Generated test cases are NOT_RUN templates.
  • The audit is automated self-verification, not a certification or a signature.
